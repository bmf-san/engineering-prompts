# 見つける問題の型

主張と根拠を突き合わせるときに当てはめる問題の型。実務の裏取り・敵対的検証で繰り返し見つかったものをまとめた。

| 型 | 見分け方 | 直し方 | 例 |
| --- | --- | --- | --- |
| 見積もりを実績として書く | 根拠が「最大」「潜在的」「見込み」の値を出している | 実績と見積もりを書き分ける | 「最大 N 社の連携が止まった」→ エラーを確かめたのは数サービスで、N 社は潜在的な影響の見積もりだった |
| 主語を広げる | 根拠に出てくるのが一部の機能・チーム・事例だけ | 根拠に出てくる範囲に主語を絞る | 「社内の AI 機能は〜している」→ そうしているのは 1 つの機能だけだった |
| 内訳を見ずに件数を使う | 件数が主張のテーマ以外のものを含んでいる | 主張に関係する件数を内訳から出す | 「事故が 16 件」→ 主張のテーマ（情報が見えてはいけない人に見えた）に当たるのは 8 件だった |
| 集計の範囲が主張と違う | 統計が原因を問わない集計、期間が古い、対象が別 | 確度に集計の範囲を書く。合わなければ使わない | 漏えいの統計が、主張している原因に絞った数字ではなかった |
| 指標の取り違え | 件数を損害額、相関を因果として書いている | 指標を根拠どおりに書く | 件数の集計を損害額として扱っていた |
| 時期・新しさの言い過ぎ | 「始めている」「新たに」など、時期を含む言葉 | 制度や文書の開始日を確かめる | 「国の制度が求め始めている」→ 指針は以前からあり、もう一方は任意の制度だった |
| 成熟度・確かさの言い過ぎ | 「成熟した」「広く使われている」「確立した」 | 根拠で言える事実（仕様が最終版になった、など）だけを書く | 「成熟した標準」→ 確かなのは最終仕様になったことだけで、実装どうしの相互運用は確かめていなかった |
| 目標と実績、対象の取り違え | 予定・目標の文書を根拠にしている | 何を、いつまでに、が根拠と一致しているか確かめる | 「12 月に開発が始まる」→ 12 月の着手が目標なのは別の仕組みだった |
| 因果の言い過ぎ | 「〜して改善した」「〜により」 | 根拠が時系列しか示さないなら、時系列の書き方にする | 「設定を見直して滞留を抑えた」→ 見直した変更自体が改善を見込んでいなかった。「見直した後は縮んだ」と書く |
| 孫引き | 根拠が別の文書の要約を引いている | 一次ソースに当たり直す | 制度の適用条件を、要約記事ではなく所管官庁の説明資料で確かめ直した |
| 古くなった事実 | ポストモーテム、リポジトリ、計画など変わるものを根拠にしている | 最新を見て、確認日を更新する | ポストモーテムが更新され、影響を受けた人数と悪用の有無の書き方が変わっていた |
| 片側だけの根拠 | コストだけ、リスクだけなど、判断の一方の材料しかない | 反対側の材料を探し、無ければ「確認できていないこと」に書く | 価格の材料だけで、収益への効き方を示す材料がなかった |
| 推定のまま | ファイル名、命名、断片から内容を推定している | 元を読んで確かめる。残ったものは「推測」と書く | ファイル名から推定した権限の分類を、コードを読んで確かめた |
| 拾い漏れ | 主張の範囲にある文書・事例を見ていない | 対象の一覧（main の文書など）を最新で取り直す | まだ拾っていない設計文書が 5 本あった |
