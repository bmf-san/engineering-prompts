# 原則の骨子

技術基準の原則と価値基準の原則のアウトラインと、各節に何を書くかの説明。文例は一例であり、書く対象は節ごとの「書くこと」で判断する。

## 技術基準の原則のアウトライン

```markdown
# <対象領域>の設計原則

## 目的
## スコープ
## 原則とは
### 原則にする基準
### 原則にしないもの
### 逸脱の扱い
## いつ使うか
## 重視する品質特性
## 原則
## ケーススタディ
## 関連リンク
```

なぜこの文書があるか（目的、性格、基準）を読ませてから規定に入る。順序を入れ替えると、規定だけが読まれ、根拠を持たないまま引用される。

| 節 | 答える問い |
| :--- | :--- |
| 目的 | この文書があると何がそろうか |
| スコープ | どの判断に使い、どの判断に使わないか |
| 原則とは | この文書は何であり、何ではないか |
| 原則にする基準／しないもの | 何を載せ、何をどこに置くか |
| 逸脱の扱い | 守れないときどうするか、何が起きたら見直すか |
| いつ使うか | 誰がどの場面で引くか |
| 重視する品質特性 | 何のために守るのか |
| 原則 | 既定として何を採るか |
| ケーススタディ | 実際にどう効いたか |
| 関連リンク | 根拠と詳細はどこにあるか |

## 価値基準の原則のアウトライン

```markdown
# 意思決定の原則

## 概要
## 目的
## スコープ
## いつ使うか
## 原則にする基準と逸脱の扱い
## 優先順位：<価値 A> > <価値 B> = <価値 C>
## <考え方 1>
## <考え方 2>
## ...
## 原則の適用例
## 関連
```

優先順位を考え方より先に置く。考え方どうしが競合したときに、どちらを取るかを先に決めておくためである。

| 節 | 答える問い |
| :--- | :--- |
| 概要 | これは何の原則か |
| 目的 | 軸が競合したとき、何がそろうか |
| スコープ | どの判断に使い、どの判断に使わないか |
| いつ使うか | 誰がどの場面で引くか |
| 原則にする基準と逸脱の扱い | 何を載せ、何をどこに置くか。守れないときどうするか |
| 優先順位 | 何を優先し、なぜその順か |
| 考え方 | 判断の重さと進め方を、何で変えるか |
| 原則の適用例 | 実際の判断で、どの原則が効いたか |
| 関連 | 進め方を定めるガイドラインと、技術基準の原則はどこにあるか |

## 各節に何を書くか

### 目的

書くこと: この文書を引くことで、誰の、どの判断が、どうそろうかを 1〜2 文で書く。

判断の基準: この文書を引いて決めたい具体的な判断を 3 つ挙げられるか。

書かないこと: 背景の長い説明、プロジェクトの経緯。それらは関連リンク先に置く。

### スコープ

書くこと: 対象とする判断と、対象外の判断（組織や事業の判断、隣の領域）と、その扱い（エスカレーション、別の原則）。

判断の基準: 読者が、目の前の判断にこの文書を使ってよいかを決められるか。

### 原則とは

書くこと: この文書に載っているものの性格。要件ではなく方針であること、人間の判断が要るものであること、個別の判断ではなく一般則であること。

判断の基準: この節だけを読んだ人が、文書の拘束力の強さを正しく見積もれるか。

### 原則にする基準／原則にしないもの（価値基準では「原則にする基準と逸脱の扱い」）

書くこと: 項目を載せるかどうかの判定条件。収録基準は「すべて満たすもの」として列挙する。除外するものは、置き場とともに「原則にしないもの → 置き場」の形で書く。

判断の基準: 既存の項目をこの基準にかけたとき、すべて通るか。通らない項目があるなら、項目か基準のどちらかが間違っている。

### 逸脱の扱い

書くこと: 単発の逸脱の記録先（PR、DesignDoc、ADR）、繰り返す逸脱のときに文書を更新すること、更新条件。

判断の基準: 逸脱を禁止していないか。更新条件が「継続的に更新する」で終わっていないか。

### いつ使うか

書くこと: 誰がどの場面でこの文書を引くかを、チーム内とチーム外に分けて列挙する。

判断の基準: 挙げた場面のそれぞれについて、この文書を開いて実際に答えが出せるか。

### 重視する品質特性

書くこと: この領域で何を守るのかを、既存の標準（ISO/IEC 25010 など）の語彙で 3 つ前後に絞って挙げる。各特性に、なぜこの領域でその特性が効くのかを、破られたときに何が起きるかで書く。前提として扱わない特性と、特性間に優先順位を置くかどうかも書く。

判断の基準: すべての原則が、ここに挙げた特性のどれかに接地しているか。

書かないこと: 特性の一般的な定義の引き写し。標準へのリンクで足りる。

### 原則（技術基準）

書くこと: 1 行 = 1 原則の表。

| 列 | 何を書くか |
| :--- | :--- |
| # | ケーススタディ、ADR、PR から「原則 3」と引くための番号 |
| 原則 | 何を既定とするかを動詞で言い切った短い名前 |
| 品質特性 | 接地先。複数可 |
| 内容 | 規定と、守らなかったときに何が起きるか |
| 設計で確認すること | レビューでそのまま引ける Yes/No の問い |

判断の基準: 項目数は 5〜7。各行が収録基準を通るか。判定できない語が入っていないか。

### 優先順位（価値基準）

書くこと: 競合しうる価値を不等号でつないだ見出しと、なぜその順かの説明。同格のものは同格と書く。上位の判断で動く価値は、原則では下に固定し、上から降りてくる経路を書く。

判断の基準: 2 つの価値が競合する具体的な場面を思い浮かべたとき、この節だけで選べるか。

### 考え方（価値基準）

書くこと: 動詞で言い切った見出しと、2〜3 行の箇条書き。各考え方に、それを引くと判断の進め方がどう変わるかを書く。

判断の基準: 各考え方が、優先順位と矛盾しないか。適用例のどれかで効いているか。効いていない考え方は飾りになる。

### ケーススタディ（技術基準）／原則の適用例（価値基準）

書くこと: 原則を実際の判断に当てはめた事例。技術基準は「事例と状況／原則／判断／トレードオフ・再検討条件／記録」、価値基準は「案件／状況／効いた原則／結論」。策定時は検証として 3 つ以上を通し、公開後は判断のたびに追記する。逸脱事例と未決事例を含める。

判断の基準: 実際に下した判断が、この文書を使って同じ結論にたどり着けるか。

### 関連リンク（価値基準では「関連」）

書くこと: 接地先の選定根拠になった上位の意思決定（ADR など）、準拠する標準、詳細を委ねている文書、ガイドライン。

判断の基準: 本文中の主張のうち、根拠を外部に置いているものがすべてここからたどれるか。

## 共通の書き方

- 空欄を残さない。未決なら「未決」と書き、決める場所を指す
- 名前は動詞で言い切る
- 規定には理由を添える。「〜する」で終わらせず、「さもなければ〜になる」まで書く
- リンクは記録に張る。本文では根拠を述べ、詳細は ADR や DesignDoc へ送る
- ケーススタディは本体と同じ変更で埋める。後から書くと埋まらない

## 記入例

一例であり、この書き方に合わせる必要はない。

### 技術基準の原則

```markdown
## 重視する品質特性

<対象領域>は次の特性を重視する。原則はこれらを守るための既定である。特性の定義は ISO/IEC 25010 に準拠する。

- <特性>（<副特性>）: <なぜこの領域でこの特性が効くか。破られたとき何が起きるか>

<優先順位を置くか置かないかを明記する。置かないなら衝突時にどこで判断するかを書く。>

## 原則

| # | 原則 | 品質特性 | 内容 | 設計で確認すること |
| --- | --- | --- | --- | --- |
| 1 | <動詞で言い切る> | <特性> | <規定>。<守らなかったときに何が起きるか>。 | <Yes/No で答えられる問い> |

## ケーススタディ

| # | 事例と状況 | 原則 | 判断 | トレードオフ・再検討条件 | 記録 |
| --- | --- | --- | --- | --- | --- |
| 1 | <見出し><br><状況> | <3 検証><br><1 独立> | <何を採り、何を捨てたか> | <受け入れた不利益><br>再検討: <条件> | [<ADR / DesignDoc>](<URL>) |
```

### 価値基準の原則

```markdown
## 優先順位：<価値 A> > <価値 B> = <価値 C>

<三つが競合するときの順と、なぜその順か。上から降りてくる判断の経路。>

## <考え方を動詞で言い切る>

- <どういう場面で>、<どう進めるか>
- <守らなかったときに何が起きるか>

## 原則の適用例

| 案件 | 状況 | 効いた原則 | 結論 |
| --- | --- | --- | --- |
| [<Issue / ADR>](<URL>) | <状況> | <原則名>（<何と何の間で>） | <結論> |
```
