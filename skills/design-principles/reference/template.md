# 設計原則の骨子

アウトラインと、各節に何を書くかの説明。文例はあくまで一例であり、**書く対象は節ごとの「書くこと」で判断する**。

## アウトライン

```markdown
# <対象領域>の設計原則

## 目的
## 原則とは
### 原則にする基準
### 原則にしないもの
### 逸脱の扱い
## いつ使うか
## 重視する品質特性
## 原則
## ケーススタディ
## 関連リンク
```

節の順序は変えない。「なぜこの文書があるか（目的・性格・基準）」を読ませてから規定に入る順序であり、入れ替えると規定だけが読まれ、根拠を持たないまま引用される。

| 節 | 答える問い |
|---|---|
| 目的 | この文書があると何が揃うか |
| 原則とは | この文書は何であり、何ではないか |
| 原則にする基準／しないもの | 何を載せ、何を載せないか |
| 逸脱の扱い | 守れないときどうするか |
| いつ使うか | 誰がどの場面で引くか |
| 重視する品質特性 | 何のために守るのか |
| 原則 | 既定として何を採るか |
| ケーススタディ | 実際にどう効いたか |
| 関連リンク | 根拠と詳細はどこにあるか |

## 各節に何を書くか

### 目的

**書くこと**: この文書を引くことで、誰の・どの判断が・どう揃うかを1〜2文で書く。

**判断の基準**: 目的が「品質を上げる」「ベストプラクティスをまとめる」のように測れない言葉になっていないか。この文書を引いて決めたい具体的な判断を3つ挙げられるなら、目的は十分に絞れている。

**書かないこと**: 背景の長い説明、プロジェクトの経緯。それらは関連リンク先に置く。

### 原則とは

**書くこと**: この文書に載っているものの性格を宣言する。読者が「違反したら即アウトなのか」「lint で弾かれるのか」を誤解しないための節。

次の3点を読者と共有する。

- 要件ではなく方針であること（逸脱は記録すれば許される）
- 人間の判断が要るものであること（機械的に判定できるものは含まない）
- 個別の判断ではなく一般則であること（合わなくなれば更新する）

**判断の基準**: この節だけを読んだ人が、文書の拘束力の強さを正しく見積もれるか。

### 原則にする基準／原則にしないもの

**書くこと**: 項目を載せるかどうかの判定条件。**この文書のスコープそのもの** であり、項目の乱立と形骸化を同時に止める唯一の仕掛けになる。

収録基準は「すべて満たすもの」として列挙する。少なくとも次を含める。

- 上位（品質特性）に接地しているか
- 判断が分かれるか（反対側にも合理性があるか）
- 特定の技術・実装・時期を前提にしていないか
- 繰り返し参照されるか
- 既存項目の言い換えでないか

除外基準は、**読者が「これも書くべきでは」と持ち込みがちなもの** を先回りして名指しする。標準・法令がすでに定めている要件、機械的に判定できるルール、特定技術の選択、期間限定の方針、数値目標、対象領域外の判断など。

**判断の基準**: 既存の項目をこの基準にかけたとき、すべて通るか。通らない項目があるなら、項目か基準のどちらかが間違っている。

### 逸脱の扱い

**書くこと**: 守れないときの扱いと、文書自体の更新条件。

- 単発の逸脱をどこに記録するか（PR、DesignDoc、ADR）
- 同じ逸脱が繰り返されたときに何をするか（文書側を更新する）
- 何が起きたら見直すか（更新条件）

**判断の基準**: 逸脱を禁止していないか。禁止された原則は、守られないか、判断を歪めてでも守られるかのどちらかになる。更新条件が「継続的に更新する」で終わっていないか。

### いつ使うか

**書くこと**: 誰がどの場面でこの文書を引くかを、チーム内とチーム外に分けて列挙する。

この節は読者への案内であると同時に、**文書の粒度を決める**。読者が外部に及ぶなら、語彙の定義と判断の根拠を本文に明示する必要がある。内部限定なら前提を省ける。

**判断の基準**: 挙げた場面のそれぞれについて、この文書を開いて実際に答えが出せるか。出せない場面があるなら、項目が足りていない。

### 重視する品質特性

**書くこと**: この領域で何を守るのかを、既存の標準（ISO/IEC 25010 など）の語彙で3つ前後に絞って挙げる。各特性には **なぜこの領域でその特性が効くのか** を、破られたときに何が起きるかで書く。

特性間に優先順位を置くかどうかを明記する。置かないなら、衝突したときにどこで判断するか（具体の設計、ADR）を書く。

**判断の基準**: すべての原則が、ここに挙げた特性のどれかに接地しているか。接地先のない特性は挙げる必要がなく、接地先のない原則は原則ではない。

**書かないこと**: 特性の一般的な定義の引き写し。定義は標準へのリンクで足りる。

### 原則

**書くこと**: 本体。1行 = 1原則の表にする。列は **番号／名前／品質特性／内容／設計で確認すること**。

| 列 | 何を書くか |
|---|---|
| # | 番号。ケーススタディ・ADR・PR から「原則 3」と引くための識別子 |
| 原則 | 何を既定とするかを動詞で言い切った短い名前 |
| 品質特性 | 接地先。複数可 |
| 内容 | 規定と、**守らなかったときに何が起きるか** |
| 設計で確認すること | レビューでそのまま引ける、Yes/No で答えられる問い |

**判断の基準**: 項目数は5〜7。10 を超えたら言い換えが混ざっている。各行が収録基準を通るか。「適切に」「うまく」など判定できない語が入っていないか。

### ケーススタディ

**書くこと**: この原則を実際の判断に当てはめた事例。列は **事例と状況／引いた原則／判断／トレードオフ・再検討条件／記録リンク**。

策定時は検証として3つ以上を通し、公開後は判断のたびに追記する。**逸脱事例と未決事例を必ず含める**。適用に成功した例だけを並べると、現実を通していない文書と見なされる。

**判断の基準**: 実際に下した判断が、この文書を使って同じ結論に辿り着けるか。辿り着けないなら、原則が足りないか粒度が違う。

### 関連リンク

**書くこと**: 品質特性の選定根拠になった上位の意思決定（ADR など）、準拠する標準・規格、詳細を委ねている文書。

**判断の基準**: 本文中の主張のうち、根拠を外部に置いているものがすべてここから辿れるか。

## 共通の書き方

- **空欄を残さない**。未決なら「未決」と書き、決める場所を指す。空欄は「検討していない」と読まれる。
- **名前は動詞で言い切る**。名詞の羅列（「可用性」「最小権限」）は規定にならない。
- **規定には必ず理由を添える**。「〜する」で終わらせず「さもなければ〜になる」まで書く。
- **リンクは記録に張る**。本文では根拠を述べ、詳細は ADR・DesignDoc へ送る。
- **ケーススタディは本体と同じ PR で埋める**。後から書くと埋まらない。

## 記入例

一例であり、この書き方に合わせる必要はない。

```markdown
## 重視する品質特性

<対象領域>は次の特性を重視する。原則はこれらを守るための既定である。特性の定義は ISO/IEC 25010 に準拠する。

- **<特性>**（<副特性>）: <なぜこの領域でこの特性が効くか。破られたとき何が起きるか>

<優先順位を置くか置かないかを明記する。置かないなら衝突時にどこで判断するかを書く。>

## 原則

| # | 原則 | 品質特性 | 内容 | 設計で確認すること |
| --- | --- | --- | --- | --- |
| 1 | <動詞で言い切る> | <特性> | <規定>。<守らなかったときに何が起きるか>。 | <Yes/No で答えられる問い> |

## ケーススタディ

| # | 事例と状況 | 原則 | 判断 | トレードオフ・再検討条件 | 記録 |
| --- | --- | --- | --- | --- | --- |
| 1 | **<見出し>**<br><状況> | <3 検証><br><1 独立> | <何を採り、何を捨てたか> | <受け入れた不利益><br>再検討: <条件> | [<ADR / DesignDoc>](<URL>) |
```
