# 設計原則の策定

設計原則とは、**設計判断において既定として採る方針** である。要件ではなく方針であり、基本は守るが逸脱は例外として記録する。原則を定める狙いは正しさの宣言ではなく、**分岐点で毎回ゼロから議論しない状態** を作ることにある。

原則があると、レビュー指摘に根拠が生まれ、他チームが相談の前に自分で判断でき、**逸脱を逸脱として認識できる**ようになる。原則がなければ、逸脱は単に「そういう実装」として通過する。

活動の進め方そのものを定めるなら原則ではなくガイドラインを使う（skill: `guideline-authoring`）。単一の意思決定を記録するなら ADR を使う（skill: `adr`）。**原則は決定の前提となる既定方針、ADR はその前提のもとで下した個別決定の記録** であり、両者は参照し合う。

## いつ使うか

- 対象領域（認証、データ基盤、API など）の設計方針をチームで揃えたいとき
- 「レビュー指摘が人によって違う」「同じ設計論争を繰り返している」「相談が特定の人に集中する」を解きたいとき
- 骨子をそのまま使いたいとき → [reference/template.md](reference/template.md)

## 原則の性質

原則に置くのは次を満たすものだけである。

- **人間の判断が要る**: 機械的に判定できるものは lint・CI・IaC に落とす。文書に残すのは判定できないものだけ
- **一般則である**: 個別の判断ではなく、繰り返し参照される。合わなくなれば更新する
- **方針である**: 守れないときは逸脱として記録すればよい。要件のように違反が即失格になるものではない

## 策定プロセス

### 1. 対象領域と読者を決める

やること:

1. 対象領域の線を引く。**原則が答えない領域**（隣接領域、上位の事業判断）を先に書く
2. 読者をチーム内・チーム外に分ける

読者が外部に及ぶなら、語彙の定義と判断の根拠を明示する必要がある。**ここで粒度が決まる**ので、先に決めてから書き始める。

### 2. 守る品質特性を決める

原則は「何のために守るのか」に接地していないと、事情が変わったときに更新も逸脱もできない。

やること:

1. 対象領域が重視する品質特性を **3つ前後** 挙げる。定義は ISO/IEC 25010 など既存の標準に準拠し、自前の分類を発明しない
2. 各特性に「なぜこの領域でこの特性が効くか」を **破られたときに何が起きるか** で書く
3. 特性間に優先順位を置くか置かないかを明記する。置かないなら、衝突時にどこで判断するか（具体の設計、ADR）を書く

品質特性の選定根拠が上位の意思決定（アーキテクチャ ADR、事業上の制約）にあるなら、そこへリンクする。

### 3. 素材を集める

**理想から書き始めない。すでに下した判断から逆算する。**

素材の在処:

- 過去の DesignDoc・ADR とその議論
- PR・設計レビューの指摘（同じ指摘が繰り返されているなら、それは原則の候補）
- 他チームからの相談・要望と、それに返した回答
- 障害・インシデントとその再発防止策
- 受け入れた妥協と、その理由

### 4. 素材を分岐点に言い換える

素材のうち **判断が分かれた点だけ** を残す。「誰も反対しないもの」は書かなくても守られるので落とす。

各素材について問う。

- 反対側の選択にも合理性があったか。なかったなら原則にしない
- その判断は他の場面でも同じ問いになるか。ならないなら個別の ADR で足りる
- 特定の実装・時期・体制を前提にしていないか。しているなら一般化するか捨てる

### 5. 収録基準と除外基準を書く

**基準を文書のなかに書く。** これが項目の乱立を止める唯一の仕掛けであり、最も飛ばされやすい工程でもある。

収録基準の既定（すべて満たすもの）。

- **特性を守る**: 重視する品質特性のどれを守るかを言える
- **判断が分かれる**: 守らない選択にも合理性がある
- **層を横断する**: インフラ・アプリケーション・運用のどこで判断しても同じ問いになる
- **繰り返し使う**: 当てはまる判断を2つ以上、具体的に想定できる
- **他の原則から導けない**: 言い換えや特殊化なら、既存原則の「確認すること」に足す

除外基準の既定。

- 標準・法令がすでに定めている要件（引用で足りる）
- 機械的に判定できるルール
- 特定の技術・実装の選択
- 期間を限った方針、移行期だけの取り決め
- 数値目標（SLO、RPO/RTO）
- 対象領域外の判断

### 6. 項目に落とす

1行 = 1原則の表にする。列は **番号／名前／品質特性／内容／設計で確認すること**。

守ること:

- **名前は動詞で言い切る**（「失敗は安全側に倒す」）。名詞の羅列（「可用性」「最小権限」）は規定にならない
- **内容に「なぜ」を入れる**。規定で終わらせず、**守らなかったときに何が起きるか** まで書く
- **「設計で確認すること」を必ず付ける**。レビューでそのまま引ける、Yes/No で答えられる問いにする。これが無い原則は宣言で終わり、使われない
- **「適切に」「うまく」「十分に」を使わない**
- **5〜7項目に絞る**。10 を超えたら言い換えが混ざっている。統合するか確認事項へ落とす
- 番号を振る。ケーススタディ・ADR・PR から「原則 3」と引けるようにする

### 7. 逸脱の扱いを設計に織り込む

**逸脱を禁止しない。** 禁止された原則は、守られないか、判断を歪めてでも守られるかのどちらかになる。

- 単発の逸脱: PR・DesignDoc に理由を残す。重い判断なら ADR を起こす
- 繰り返す逸脱: 原則が現実に合っていないサイン。ADR を起こして原則を更新する
- 保留・未決: 空欄にせず「未決」と書き、決める場所を指す

更新条件も書く。「継続的に更新する」だけでは更新されない。**何が起きたら見直すか**（同じ逸脱が2回／準拠する標準が改訂／移行フェーズの完了）を具体的に書く。

### 8. ケーススタディで検証する

**すでに下した判断を3つ以上、原則に通す。** 通らなければ、原則が足りないか粒度を誤っている。策定の検証であり、同時に読者にとっての使い方の手本になる。

列は **事例と状況／引いた原則／判断／トレードオフ・再検討条件／記録リンク**。

- **逸脱事例と未決事例を必ず含める**。きれいな適用例だけの原則は、現実を通していないと見なされる
- 逸脱は「原則 4 からの逸脱」と明記し、再検討条件を書く

### 9. 合意して運用に載せる

原則は個人の主張ではなくチームの合意である。書き上がってからレビューに出すのではなく、**項目名と収録基準の段階で合意を取る**（skill: `adr` の「議論を経てから書く」と同じ理由）。

引かれる場所を作る。

- DesignDoc・ADR のテンプレートから参照させ、設計の出発点にする
- レビュー指摘の根拠として番号で引く
- 他チームへの回答の根拠として示し、個別交渉にしない

## 策定後の自己点検

次のいずれかが当てはまったら、項目を足すのではなく **基準と接地を疑う**。

| サイン | 示していること |
|---|---|
| 誰も反対しない項目が並ぶ | 「判断が分かれる」を通していない（4・5節） |
| 「適切に」「うまく」が多い | 判定できず、レビューで引けない（6節） |
| 項目が10を超える | 上位項目の言い換えが混ざっている（6節） |
| ケーススタディが空 | 現実の判断を通して検証していない（8節） |
| 確認する問いがない | 宣言で終わっており、使われない（6節） |
| 逸脱の扱いがない | 現実と衝突した瞬間に無視される（7節） |
| 半年以上更新がない | 更新条件を書いていないか、引かれる場所がない（7・9節） |
