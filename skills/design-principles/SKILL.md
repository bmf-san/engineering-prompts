# 原則の策定

原則は、判断において既定として採る方針である。要件ではなく方針であり、基本は守るが、逸脱は例外として記録する。狙いは正しさの宣言ではなく、分岐点で毎回ゼロから議論しない状態を作ることにある。

原則があると、設計するとき、レビューするとき、相談や要望に答えるときのいずれでも同じ根拠を引ける。書いた側も読んだ側も、エスカレーションの前に自分で決められる。既定が明示されていることで、逸脱を逸脱として認識できる。原則がなければ、逸脱は単に「そういう実装」として通過する。

## いつ使うか

- 判断の軸が競合したとき（安全性と速度など）に、担当者によって選ぶ側が変わるのを止めたいとき
- 対象領域（認証、認可、データ基盤、API など）の設計方針をチームでそろえたいとき
- レビュー指摘が人によって違う、同じ設計論争を繰り返している、相談が特定の人に集中する、を解きたいとき
- 既存の原則が引かれていない、形骸化しているので見直すとき

活動の進め方を定めるなら `guideline-authoring`、単一の意思決定を記録するなら `adr` を使う。原則は決定の前提となる既定であり、ADR はその前提のもとで下した個別決定の記録である。両者は参照し合う。トレードオフの対立が本物かを吟味するところは `critical-thinking` を使う。

## 原則の性質

原則に置くのは、次を満たすものだけである。

- 人間の判断が要る。機械的に判定できるものは lint、CI、IaC に落とす
- 一般則である。個別の判断ではなく、繰り返し参照される。合わなくなれば更新する
- 方針である。守れないときは逸脱として記録すればよい。要件のように違反が即失格になるものではない

## 1. 原則の種類を決める

原則には 2 つの種類がある。答える問いと接地先が違うので、1 つの文書に混ぜない。

| 種類 | 答える問い | 接地先 | 本体の形 | 例 |
| :--- | :--- | :--- | :--- | :--- |
| 価値基準の原則 | 軸が競合したとき、何を優先するか。判断の重さをどう変えるか | 判断の再現性（担当者や場面によらず同じ順で選べること） | 優先順位と、少数の考え方の見出し＋箇条書き | 意思決定の原則（安全性 > 速度 = 再現性、可逆性で判断の重さを変える、不可逆な決定は遅延させる、トレードオフを考える、判断を記録する） |
| 技術基準の原則 | その領域で、何を良しとするか | 領域が重視する品質特性 | 番号つきの表（原則／品質特性／内容／設計で確認すること） | 認証の設計原則（独立して成立させる、持つものは最小にする、失敗は安全側に倒す） |

やること:

1. 解きたい揺れが、優先順位の揺れか、領域の技術基準の揺れかを見分ける
2. 価値基準の原則は、チームで 1 つにする。領域をまたいで同じ優先順位を使う
3. 技術基準の原則は、領域ごとに 1 つにする。隣の領域の判断は、その領域の原則に委ねる
4. ガイドラインとの分担を決める。ガイドラインは判断の軸と問いを持ち、優先順位は価値基準の原則に、領域固有の基準は技術基準の原則に委ねる

守ること:

- 価値基準の原則に、領域固有の技術基準を書かない。領域が増えるたびに肥大する
- 技術基準の原則に、チーム全体の優先順位を書かない。領域ごとに優先順位が食い違う

## 2. 対象と読者を決める

やること:

1. 対象の線を引く。原則が答えない範囲（隣の領域、組織や事業の判断）を先に書く
2. 読者をチーム内とチーム外に分け、それぞれがどの場面で引くかを書く

守ること:

- 読者が外部に及ぶなら、語彙の定義と判断の根拠を明示する。ここで粒度が決まるので、先に決めてから書き始める

## 3. 接地先を決める

原則は、何のために守るのかに接地していないと、事情が変わったときに更新も逸脱もできない。

価値基準の原則なら:

1. 競合しうる価値を 3 つ前後挙げる（安全性、速度、再現性など）
2. 優先順位を不等号で固定する（安全性 > 速度 = 再現性）。同格のものは同格と書く
3. なぜその順なのかを書く。上位の判断で動く価値は、原則では下に固定し、上から降りてくる経路を書く（例: 速度を優先すべき場面は事業観点で判断され、レポートラインから降りてくるので、原則としては安全性を上に固定する）

技術基準の原則なら:

1. 対象領域が重視する品質特性を 3 つ前後挙げる。定義は [ISO/IEC 25010](https://iso25000.com/index.php/en/iso-25000-standards/iso-25010) など既存の標準に準拠し、自前の分類を発明しない
2. 各特性に、なぜこの領域でこの特性が効くかを、破られたときに何が起きるかで書く
3. 特性間に優先順位を置くか置かないかを明記する。置かないなら、衝突時にどこで判断するか（具体の設計、ADR）を書く
4. 前提として扱わない特性（機能適合性など）を書く

守ること:

- 接地先の選定根拠が上位の意思決定（アーキテクチャの ADR、事業上の制約）にあるなら、そこへリンクする

## 4. 素材を集める

理想から書き始めない。すでに下した判断から逆算する。

やること:

1. 素材を集める。過去の DesignDoc、ADR とその議論、PR や設計レビューの指摘、他チームからの相談と返した回答、障害とその再発防止策、受け入れた妥協とその理由
2. 判断が分かれた点だけを残す。誰も反対しないものは、書かなくても守られるので落とす
3. 各素材に問う。反対側の選択にも合理性があったか（なければ原則にしない）。他の場面でも同じ問いになるか（ならなければ ADR で足りる）。特定の実装、時期、体制を前提にしていないか（していれば一般化するか捨てる）

守ること:

- 同じ指摘が繰り返されているレビューは、原則の候補として優先して拾う

## 5. 原則にする基準と、しないものの置き場を書く

基準を文書のなかに書く。項目の乱立を止める唯一の仕掛けであり、最も飛ばされやすい工程でもある。

原則にする基準（すべて満たすもの）:

- 接地先を守る: 重視する品質特性や価値のどれを守るかを言える
- 判断が分かれる: 守らない選択にも合理性があり、放っておくと判断が分かれる
- 層を横断する: インフラ、アプリケーション、運用のどこで判断しても同じ問いになる
- 繰り返し使う: 当てはまる判断を 2 つ以上、具体的に想定できる
- 他の原則から導けない: 言い換えや特殊化なら、既存原則の確認事項に足す

原則にしないものは、置き場とともに書く:

| 原則にしないもの | 置き場 |
| :--- | :--- |
| 標準や法令がすでに定めている要件 | 標準そのもの、チェックリスト |
| 機械的に判定できるルール | lint、CI、テスト |
| 特定の技術や実装の選択 | ADR |
| 期間を限った方針、移行期だけの取り決め | DesignDoc の Concerns、移行計画 |
| 数値目標（SLO、RPO/RTO） | PRD、DesignDoc |
| 対象外の領域の判断 | その領域の原則 |
| 活動の進め方 | ガイドライン |

守ること:

- 置き場を書かずに除外しない。置き場がないと、除外したものが原則に戻ってくる

## 6. 項目に落とす

やること:

1. 名前を動詞で言い切る（「失敗は安全側に倒す」「不可逆な決定は遅延させる」）
2. 内容に、なぜそうするかと、守らなかったときに何が起きるかを書く
3. 技術基準の原則は、1 行 = 1 原則の表にし、列を「番号／原則／品質特性／内容／設計で確認すること」にする。確認することは、レビューでそのまま引ける Yes/No の問いにする
4. 価値基準の原則は、優先順位を最初に置き、続けて考え方を見出しと箇条書きで書く。各考え方に、それを引くと判断の進め方がどう変わるかを書く（戻せる決定は速く試す、戻せない決定は証跡を厚くし、まず戻せる決定にできないかを考える）

守ること:

- 名詞の羅列（「可用性」「最小権限」）で終わらせない。規定にならない
- 「適切に」「うまく」「十分に」を使わない。判定できず、レビューで引けない
- 5〜7 項目に絞る。10 を超えたら言い換えが混ざっている。統合するか確認事項へ落とす
- 技術基準の原則には番号を振る。ケーススタディ、ADR、PR から「原則 3」と引けるようにする

## 7. 逸脱と更新を織り込む

逸脱を禁止しない。禁止された原則は、守られないか、判断を歪めてでも守られるかのどちらかになる。

やること:

1. 単発の逸脱は、PR や DesignDoc に理由を残すと書く。重い判断なら ADR を起こす
2. 繰り返す逸脱は、原則が現実に合っていないサインとして、ADR を起こして原則を更新すると書く
3. 保留や未決は、空欄にせず「未決」と書き、決める場所を指す
4. 更新条件を書く。何が起きたら見直すか（同じ逸脱が 2 回、準拠する標準の改訂、移行フェーズの完了）を具体的に書く

守ること:

- 「継続的に更新する」だけで終わらせない。条件が書かれていない文書は更新されない

## 8. 適用例で検証する

すでに下した判断を 3 つ以上、原則に通す。通らなければ、原則が足りないか粒度を誤っている。策定の検証であり、同時に読者にとっての使い方の手本になる。

やること:

1. 技術基準の原則は「番号／事例と状況／原則／判断／トレードオフ・再検討条件／記録」の表にする
2. 価値基準の原則は「案件／状況／効いた原則／結論」の表にする。チーム内の判断と、問い合わせや相談の回答の両方から取る
3. 逸脱事例と未決事例を含める。逸脱は「原則 4 からの逸脱」と明記し、再検討条件を書く

守ること:

- きれいな適用例だけを並べない。現実を通していない文書と見なされる
- 記録へのリンクが未整備なら、差し替え予定と書く。リンクのない結論は追えない

## 9. 合意して、引かれる場所に置く

原則は個人の主張ではなくチームの合意である。原則は参照されて初めて機能する。

やること:

1. 書き上がってからではなく、項目名と原則にする基準の段階で合意を取る（`adr` の「議論を経てから書く」と同じ理由）
2. 既存の作業導線のどこから引くかを決めてから公開する。DesignDoc や ADR のテンプレートに組み込む、レビューで番号を根拠として引く、相談への回答の根拠として示し個別交渉にしない
3. AI のレビューに引かせるなら、原則の写しを指示ファイルに置き、適用するパスを決める。各原則に「指摘する例」を添え、原則に照らせない指摘はさせない。写しには正典の場所を書き、正典を更新したら写しも直す

守ること:

- 正典を 1 つにする。写しは正典への参照を持ち、写し側で原則を変えない

## 10. 点検

書き終えたら、次の型に当てはまるところがないかを見る。当てはまったら、項目を足すのではなく基準と接地を疑う。

| 型 | 見分け方 | 直し方 |
| :--- | :--- | :--- |
| 種類が混ざっている | 優先順位と領域の技術基準が同じ文書に並ぶ | 価値基準と技術基準に分ける（1 節） |
| 接地していない | 何のために守るのかが書かれていない、優先順位の理由がない | 品質特性か優先順位とその理由を書く（3 節） |
| 誰も反対しない | 当たり前の項目が並ぶ | 判断が分かれる点だけを残す（4・5 節） |
| 除外が戻ってくる | 原則にしないものの置き場が書かれていない | 置き場とともに除外する（5 節） |
| 判定できない | 「適切に」「うまく」が多い、確認する問いがない | 動詞で言い切り、Yes/No の問いを付ける（6 節） |
| 項目が多い | 10 を超える | 言い換えを統合し、確認事項へ落とす（6 節） |
| 逸脱の扱いがない | 現実と衝突した瞬間に無視される | 逸脱の記録先と更新条件を書く（7 節） |
| 適用例が空 | 現実の判断を通して検証していない | 逸脱と未決を含めて 3 つ以上通す（8 節） |
| 引かれない | 半年以上更新がない、レビューで番号が引かれない | テンプレート、レビュー、AI の指示ファイルに組み込む（9 節） |
