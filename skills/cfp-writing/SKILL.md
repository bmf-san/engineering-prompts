# CFP を書く

採択する側が判断に使う情報を、短く過不足なく書く。CFP を書く時点で、スライドを作り始められる程度に発表の中身が整理されている状態を目指す。そのために、ネタを先に文章として書き上げておく。

## いつ使うか

- カンファレンスや勉強会の CFP に応募するとき
- 登壇のネタはあるが、提案の形にまとまっていないとき
- 提出前の CFP を見直したいとき

採択されたあとの準備は `talk-preparation` を使う。

## 1. 書く前に

やること:

1. 登壇の目的を決める。自分が得たいものと、聴き手にとっての価値の両方を書く
2. イベントを調べる。過去の発表のテーマとレベル感、聴き手の層を知る。参加したことがなければ、過去の発表資料や録画を見る
3. 日程を確かめる。採択されてから出られないことがないよう、先に調整しておく
4. 採択基準と行動規範を読む。枠の長さ、文字数、締切などの応募条件を写す
5. 応募フォームの欄を写す。欄の名前、文字数の上限、必須かどうか、書き方の指定（形式、言語、書いてはいけないこと）を控える

## 2. ネタを文章にする

やること:

1. ネタを記事として書き上げる。メモではなく、構成を考えた文章にする
2. 書き上げた記事を、CFP の本文とアウトライン、スライドの元にする

守ること:

- CFP を書き始める前に、内容がスライドを作り始められる程度に整理されているかを確かめる。整理されていなければ、先に記事を書く

## 3. 整理する

次の項目を、順不同で埋める。雛形は [reference/template.md](reference/template.md) にある。

| 項目 | 書くこと |
| --- | --- |
| セッションタイトル | 一息で発表の中身が伝わる名前。関数や変数に名前を付けるときと同じ考え方で付ける。決まらなければ仮で置く |
| 話すこと・話さないこと | 特に、話さないことを書く。一番伝えたいことに関係の薄い話を外し、内容が散らばらないようにする |
| 伝えたいこと | 1 つに絞る |
| キーワード | 発表に関わる語を書き出す。広げるためではなく、要点と、触れなくてよいものを見分けるために使う |
| アウトライン | 記事があれば、記事から起こす |
| 調査 | あとで確かめること。事実確認、技術検証、サンプル実装など |

## 4. 本文を書く

やること:

1. 応募フォームの欄ごとに、3 で整理した内容から書く。欄の指定がなければ、次の順で書く
   1. 何について話すか
   2. 誰に向けた話か
   3. 聴き手が持ち帰れるもの
   4. アウトライン
   5. 補足資料のリンク（記事、リポジトリ、過去のスライドなど）
2. 欄ごとに、文字数の上限と書き方の指定を守っているかを確かめる
3. 採択する側の立場で読み直す

守ること:

- イベントが決めた形式に従う。欄の名前や順番を自分の構成に合わせて変えない
- 上の順番の項目に当たる欄がなければ、その項目は入る欄に収める。収まらなければ削る
- 文字数に余裕があっても短く書く。採択する側が判断に使う情報が入っていれば足りる
- 過去の発表を発展させる場合は、前回から何を足したかを書く
- 本文とは別に審査向けの補足欄があれば、補足は本文に混ぜずにそちらへ書く
