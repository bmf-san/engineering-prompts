# イベントストーミング

ドメインで起きる出来事を、過去形の短い文（ドメインイベント）にして時系列に並べる。並べる過程で、関係者の理解のずれ、業務のルール、責任の境界を見つける。

## いつ使うか

- 新しいドメインや、複数チームにまたがる業務を理解したいとき
- 関係者の間で、業務の流れの理解がそろっていないとき
- システムをどこで分けるか（境界づけられたコンテキスト、サービス、チーム）を考えたいとき
- 機能を設計する前に、業務のルールと例外を洗い出したいとき

要件と制約の切り分けは `requirements-engineering`、見つけた境界をサブドメインとして分類し、コンテキストの関係を決めるところは `strategic-design`、分割の方針を戦略として決めるところは `architecture-strategy`、見つかった課題の整理は `problem-framing` を使う。

## 1. 目的と粒度を決める

やること:

1. 何のために行うかを一文で書く。理解をそろえる、課題を見つける、設計の境界を決める、など
2. 粒度を選ぶ

   | 粒度 | 扱う範囲 | 向いている目的 |
   | :--- | :--- | :--- |
   | ビッグピクチャー | 事業やドメイン全体 | 全体の理解、課題と境界の発見 |
   | プロセスモデリング | 一つの業務の流れ | 流れとルール、例外の洗い出し |
   | ソフトウェア設計 | 一つの境界の中 | 集約、コマンド、ルールの設計 |

3. 対象の始まりと終わりを決める。例: 「申込みを受けてから、初回の請求が終わるまで」

守ること:

- 粒度を混ぜない。ビッグピクチャーで実装の話が出たら、ホットスポットに書いて先に進む

## 2. 準備する

やること:

1. 参加者を決める。業務を知っている人（ドメインエキスパート）と、作る人の両方を呼ぶ。片方だけだと、もう片方の視点が抜ける
2. 場所を用意する。長い壁か、横に広いオンラインボードを使う。時間軸を左から右に取れる広さにする
3. 付箋の種類と色を決め、凡例を貼る。種類は [reference/notation.md](reference/notation.md) にある
4. ファシリテーターを一人決める。ファシリテーターは内容に答えを出さず、進行と問いかけに徹する

## 3. 出来事を出す

やること:

1. 参加者がそれぞれ、ドメインで起きる出来事を付箋に書いて貼る。この段階では順番も重複も気にしない
2. 出来事は過去形で書く。「注文が確定した」「請求書が送られた」
3. 出尽くしたら、時系列に並べ直す。重複はまとめ、同じ言葉で違うものを指していないかを確かめる
4. 流れの区切りになる出来事（ピボットイベント）を見つけ、その前後で区切る

守ること:

- 正しさより、出し切ることを優先する。間違いは並べ直すときに直す
- 技術の言葉ではなく、業務で使う言葉で書く。「レコードが更新された」ではなく、業務として何が起きたかを書く
- 一人の発言で決めない。付箋で出してもらう

## 4. ホットスポットを残す

やること:

1. 疑問、意見の食い違い、分からないこと、痛みがある場所に、ホットスポットの付箋を貼る
2. その場で答えが出ないものは、ホットスポットに書いて先に進む
3. 終わったら、ホットスポットを一覧にし、誰がいつまでに確かめるかを決める

守ること:

- 議論が長引いたら、ホットスポットに書いて止める。全員の時間を一つの論点に使わない
- 意見の食い違いは、どちらかに決めずに両方を書く。食い違い自体が、境界や課題の手がかりになる

## 5. 流れを詳しくする

プロセスモデリングとソフトウェア設計の粒度で行う。

やること:

1. 出来事ごとに、それを引き起こしたもの（コマンド）と、実行した人（アクター）を置く
2. 出来事を受けて自動で起きること（ポリシー）を置く。「〜したら、〜する」
3. 判断に使った情報（リードモデル）と、関わる外部システムを置く
4. コマンド → 出来事 → ポリシー → コマンド とつながる流れが、途切れずにたどれるかを確かめる。途切れたところはホットスポットにする

## 6. 境界を見つける

やること:

1. 同じ言葉が違う意味で使われ始める場所、担当する人やチームが変わる場所、ピボットイベントの前後に線を引く。そこが境界づけられたコンテキストの候補になる
2. ソフトウェア設計の粒度では、同じルールを守る必要があるコマンドと出来事をまとめ、集約の候補にする
3. 境界をまたぐ出来事を書き出す。境界の間で受け渡す情報になる

守ること:

- 境界は候補として扱う。組織、既存システム、変えやすさを見てから決める。決めるときは `strategic-design` を使う

## 7. まとめる

やること:

1. ボードを写真か書き出しで残す
2. 次をまとめる
   - 時系列の出来事の流れ
   - ピボットイベントと、境界の候補
   - ホットスポットの一覧と、確かめる人と期限
   - 決まったこと（用語の定義、ルール）
3. 用語は、意味と、どの境界で使うかを書いて、用語集にする

## 資料から下書きする

ワークショップの前に、仕様書、業務マニュアル、問い合わせ、ログ、コードから出来事を拾って下書きを作ることがある。

やること:

1. 資料から出来事を拾い、出典を添えて時系列に並べる
2. 資料から分からないところは、推測で埋めずにホットスポットにする
3. 下書きは、ワークショップの叩き台として使う。ドメインエキスパートに確かめるまで、正しいものとして扱わない

守ること:

- 下書きだけで設計を決めない。机上で作った流れは、書き手の理解にとどまる
