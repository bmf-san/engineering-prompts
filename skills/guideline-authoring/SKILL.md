# 規範ドキュメント（ガイドライン・設計原則・規約）の作り方

チームが同じ問いに同じ答えを返せるようにするための文書を作る。狙いは正しさの宣言ではなく **判断の再現性** である。担当者・場面が変わっても判断の質が一定以上に保たれ、都度のエスカレーションなしに各自が決められる状態を作る。

作った文書が使われないのは、たいてい内容が間違っているからではなく、**載せる基準がない／確認する問いがない／逸脱の扱いが決まっていない** からである。この skill はその3点を最優先で埋める。

## いつ使うか

- ガイドライン・設計原則・規約・ポリシーを新しく作るとき
- 既存の規範ドキュメントをレビューし、形骸化・スコープ過大になっていないか判断するとき → [reference/review.md](reference/review.md)
- 「レビュー指摘が人によって違う」「同じ相談に毎回ゼロから答えている」「判断がエスカレーションに渋滞している」を解きたいとき
- 骨子をそのまま使いたいとき → [reference/template.md](reference/template.md)

単一の意思決定を記録するなら規範ドキュメントではなく ADR を使う（skill: `adr`）。**規範ドキュメントは決定の前提となる既定方針、ADR は個別決定の記録** であり、両者は参照し合う。

## 1. 文書の型を選ぶ

規範ドキュメントは層をなす。**新しく書く前に、どの層が空いているかを確認する。** 既存の層に足りるなら足すほうが、文書を増やすより機能する。

| 層 | 型 | 決めること | 技術依存 |
|---|---|---|---|
| 判断の型 | ガイドライン | どう判断するか。フロー、仕分け、エスカレーション先 | 非依存 |
| 評価の基準 | 設計原則 | 何を良しとするか。既定として採る方針 | 非依存 |
| 構造の決定 | 規約 | 特定技術の文脈で原則を具体化し、分け方と責務の置き方を決める | 依存 |
| 値・手順 | 設定値、Runbook、lint ルール | 個々のパラメータ、誰が何をするか | 依存 |
| 現況 | システムリファレンス | いま何がどうなっているか | 依存 |

守ること:

- **上の層に接地させる**。規約は原則のどれを具体化したかを言える。原則は守る品質特性を言える。接地先がない項目は、その文書の項目ではない。
- **機械的に判定できるものは下の層へ落とす**。lint・CI・IaC で判定できるなら文書に書かない。規範ドキュメントに残すのは **人間の判断が要るもの** だけ。
- **現況を混ぜない**。「いまこうなっている」は変化が速く、混ぜると文書全体が古びる。

## 2. 目的を「何が揃うか」で書く

目的は「品質を上げる」ではなく、**誰の・どの判断が・どう揃うか** で書く。

- 良い: 「同じ問いに同じ答えを返せるようにする」「担当者が変わっても同じ判断になる」「相談の前に相手が自分で判断できるようにする」
- 悪い: 「セキュアな設計を実現する」「ベストプラクティスをまとめる」

目的が測れない言葉になるときは、収録基準（3節）が作れないサインである。先に「この文書を引いて決めたい判断」を3つ具体的に挙げ、そこから目的を書く。

続けて **いつ使うかをチーム内・チーム外に分けて書く**。読者が内部だけなら前提を省けるが、外部に準拠を求めるなら語彙の定義と判断の根拠を明示する必要がある。ここで粒度が決まる。

- チーム内: 設計の出発点にする／各自が照らして決める／レビュー指摘の根拠として引く／逸脱に気づいて記録する
- チーム外: 相談の前に自分で判断する／回答の根拠として示し、個別交渉にしない

## 3. 収録基準と除外基準を先に書く

**文書のなかに「何を載せるか／載せないか」の基準を明示する。** これが項目の乱立と形骸化を同時に止める唯一の仕掛けであり、最も飛ばされやすい工程でもある。

収録基準は次をすべて満たすもの、とするのが既定。

- **上位に接地する**: 守る品質特性／具体化する原則を名指しできる
- **判断が分かれる**: 従わない選択にも合理性があり、放っておくと設計が分かれる。**誰も反対しないものは書かなくても守られる**
- **横断する**: どの層・どの場面で判断しても同じ問いになる。特定の実装・時期を前提にしない
- **繰り返し使う**: 当てはまる判断を2つ以上、具体的に想定できる
- **他の項目から導けない**: 既存項目の言い換え・特殊化なら、その項目の「確認すること」に足す
- （規約の場合）**後から変えにくい**: 決め直すコストが高い。安い判断はレビューで足りる

除外基準の既定。

- 標準・法令がすでに定めている要件（引用で足りる）
- 機械的に判定できるルール（lint・CI・IaC へ）
- 特定の技術・実装の選択（原則の場合）／個々のパラメータ値（規約の場合）
- 期間を限った方針、移行期だけの取り決め
- 数値目標（SLO、RPO/RTO など）
- 手順（誰がどこに何を出すか）
- 現況
- 対象領域外の判断

## 4. 項目は「規定 + なぜ + 確認する問い」で書く

項目は表にし、1行 = 1項目とする。

| 列 | 中身 |
|---|---|
| # | 番号。ケーススタディや PR から「原則 3」と引けるようにする |
| 名前 | 動詞で言い切る（「失敗は安全側に倒す」「Service は既定で分けない」） |
| 接地先 | 守る品質特性／具体化する上位の原則 |
| 内容 | 規定と、**守らなかったときに何が起きるか** |
| 設計で確認すること | レビューでそのまま引ける問い |

守ること:

- **「なぜ」を必ず書く**。理由のない規定は、事情が変わったときに更新も逸脱もできず、ただ無視される。
- **「確認すること」を必ず付ける**。これが無い項目は宣言で終わり、レビューで使われない。問いは Yes/No で答えられる形にする（「依存先が止まったとき、認証がどう振る舞うかを決めているか」）。
- **「適切に」「うまく」「十分に」を使わない**。判定できない語は判断を揃えない。
- **5〜7項目に絞る**。10 を超えたら上位項目の言い換えが混ざっている。統合するか、確認事項へ落とす。
- 品質特性を軸に使うなら **ISO/IEC 25010** など既存の定義に準拠する。自前の分類を作る前に既存の標準を探す。

## 5. 逸脱の扱いと更新条件を決める

**逸脱を禁止しない。** 禁止された文書は、守られないか、判断を歪めてでも守られるかのどちらかになる。

- 単発の逸脱: PR・DesignDoc に理由を残す。重い判断なら ADR を起こす
- 繰り返す逸脱: 文書が現実に合っていないサイン。ADR を起こして文書を更新する
- 保留・未決: 空欄にせず「未決」と書き、決める場所（別 DesignDoc、別 ADR）を指す

更新条件も書く。「運用しながら継続的に更新する」だけでは更新されない。**何が起きたら見直すか**（同じ逸脱が2回／前提の標準が改訂／対象システムの分離完了）を書く。

## 6. ケーススタディで接地する

**すでに下した実際の判断を3つ以上、その文書に通す。** 通らなければ、項目が足りないか粒度を誤っている。これは検証であり、同時に読者にとっての使い方の手本になる。

| 列 | 中身 |
|---|---|
| 事例と状況 | 何を判断する場面だったか |
| 引いた項目 | 原則 3、規約 2 など。**逸脱なら「4 からの逸脱」と書く** |
| 判断 | 何を採り、何を捨てたか |
| トレードオフ・再検討条件 | 受け入れた不利益と、いつ見直すか |
| 記録 | ADR・DesignDoc・Issue へのリンク |

守ること:

- **逸脱事例と未決事例を必ず含める**。きれいな適用例だけの文書は、現実を通していないと見なされる。
- 素材は過去の Issue・Slack の相談・PR レビューの指摘・障害から拾う。**ゼロから理想を書かず、下した判断から逆算する**。

## 作る手順

1. この文書を引いて決めたい判断を3つ挙げ、目的を書く
2. 層を確認し、型を選ぶ（1節）。既存文書に足せないかを先に検討する
3. 上位の軸を決める（守る品質特性、準拠する標準）。標準は **どの役割で採るか**（プロセス／採点／洗い出し／観点）まで書く
4. 素材を集める（過去の判断、Issue、相談、レビュー指摘、障害）
5. 収録基準・除外基準を書く（3節）
6. 素材を基準にかけて項目化し、5〜7 に絞る（4節）
7. 各項目に「確認すること」を付ける
8. 実際の判断3つ以上をケーススタディとして通す（6節）
9. 逸脱の扱いと更新条件を書く（5節）
10. レビューする（[reference/review.md](reference/review.md)）。公開後は逸脱と新しい判断を契機に更新する

## 形骸化のサイン

次のいずれかが当てはまったら、内容を足すのではなく **基準と接地を疑う**。

| サイン | 示していること |
|---|---|
| 誰も反対しない項目が並ぶ | 収録基準の「判断が分かれる」を通していない |
| 「適切に」「うまく」が多い | 判定できず、レビューで引けない |
| 項目が10を超える | 上位項目の言い換えが混ざっている |
| ケーススタディが空 | 現実の判断を通して検証していない |
| 確認する問いがない | 宣言で終わっており、使われない |
| 逸脱の扱いがない | 現実と衝突した瞬間に無視される |
| 半年以上更新がない | 運用されていないか、更新条件を書いていない |
