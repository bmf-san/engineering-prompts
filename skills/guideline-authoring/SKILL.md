# ガイドラインの策定

ガイドラインとは、ある活動（判断、問い合わせ対応、設計作業、アセスメント）を **担当者が変わっても同じ型で進められるようにする手引き** である。決めるのは **進め方** であって「何を良しとするか」ではない。後者は設計原則に委ねる（skill: `design-principles`）。

狙いは手順の網羅ではなく **判断の再現性** である。使われないガイドラインは、たいてい内容が薄いからではなく、**決めることと委ねることの境界が曖昧で、読んでも次の一歩が決まらない** から使われない。

## いつ使うか

- 「同じ相談に毎回ゼロから答えている」「対応の質が担当者で揺れる」「判断がエスカレーションに渋滞している」を解きたいとき
- 設計作業（監視設計、アセスメント、移行計画など）の進め方をチームで揃えたいとき
- 既存のガイドラインが参照されていない・守られていないので作り直すとき

何を良しとするかの基準を決めたいなら `design-principles`、単一の意思決定を記録するなら `adr` を使う。

## 策定プロセス

### 1. 目的を「何が揃うか」で書く

目的は「品質を上げる」ではなく、**誰の・どの活動が・どう揃うか** で書く。

- 良い: 「誰もが同じ水準で問い合わせに対応できる状態を作る」「同じ問いに同じ答えを返せるようにする」
- 悪い: 「対応品質を向上させる」「ベストプラクティスをまとめる」

目的が測れない言葉になるときは、**このガイドラインを引いて進めたい実例を3つ** 具体的に挙げ、そこから書き直す。

### 2. 境界を引く（決める・委ねる・上げる）

最初に決めるのはフローではなく **境界** である。ここが曖昧だと、読者は最後に「で、誰が決めるのか」で止まる。

| 区分 | 内容 | 書き方 |
|---|---|---|
| 決めること | 活動の進め方、仕分け、フロー | 本文で定める |
| 委ねること | 何を良しとするかの技術的基準 | 設計原則へリンクする |
| 上げること | やるか・いつやるか・誰がコストを負担するか | エスカレーション先を名指しする |

守ること:

- **技術判断（妥当か・どう作るべきか）と対応コミット（やるか・いつやるか）を分ける**。技術的に妥当でも引き受けるかは別の判断であり、混ぜると技術的な結論が組織の都合で歪む
- エスカレーション先は役割で書く。個人名で書かない
- 扱わない範囲を明示する（「本ガイドはここまで。人を呼ぶ基準と目標値は扱わない」）

### 3. 現状の型を書き出す

**理想の手順から書き始めない。すでにうまくいった対応から逆算する。**

素材の在処:

- 過去の Issue・相談スレッドと、そこで実際に辿った判断の道筋
- うまくいかなかった対応（どこで止まったか、なぜ揺れたか）
- 議事録、障害対応の記録

うまくいった対応を3件並べ、**共通して通った経路** を抜き出す。それがフローの骨格になる。

### 4. フローにする

やること:

1. 骨格を分岐つきの図（Mermaid など）にする
2. 各分岐に「何を見て分けるか」を書く
3. 各終端に「何をするか」と「誰が決めるか」を書く

守ること:

- **分岐は判断の主体・重さが変わる点に置く**（自チームかエスカレーションか、戻せる決定か戻せない決定か）。手順の細かさで分岐させない
- **分岐は3〜4に抑える**。多いフローは参照されず、結局は勘で進められる
- **入口と記録先を一箇所に固定する**。入口が散るとフローに乗る前に流れ、記録先が散ると結論だけが残って経緯が消える。やりとりと結論を同じ場所に残し、フロー情報で流さない
- **結論が否定になる終端ほど、返す内容の書式を決める**。見送り・却下は、理由・将来の可能性・代替経路をセットにする。理由だけを返すと交渉が再燃し、同じ相談が繰り返される
- フローの前後で何が入力され何が出力されるかを書く。図だけを置かない

### 5. 判断の軸を少数の汎用に保つ

評価の観点は、対象に依存しない少数の軸にする（例: 機能／非機能／境界と責務）。**領域固有の具体は設計原則に委ね、ガイドラインには軸と問いだけを置く**。ここに固有の基準を書き込むと、領域が増えるたびにガイドラインが肥大し、原則との二重管理になる。

### 6. 前提を揃えるステップを入れる

対象を説明できない状態で進めると、最初の列挙が浅くなり、以降のすべてが的を外す。**作業前に何を揃えるかをガイドラインに書く**（対象の目的・構成・既存の状況・過去の事例）。

揃っていなければこの機会に作る。前提資料が初めて作られること自体に価値がある。

### 7. 成果物テンプレートを同梱する

**コピーして使える表・雛形を本文に置く。** テンプレートのないガイドラインは読まれて終わり、成果物の粒度が揃わない。

- 各ステップの出力を表の形で定義する（列がそのままチェック項目になる）
- 記入例を1行入れる。空の表だけでは粒度が伝わらない

### 8. 既存のフレームワークに接地する

自前の手順を発明する前に、確立した骨格を探して借りる。借りるときは **どの役割で採るか** を書く（プロセス／採点／洗い出し／観点）。

- 役割を書かないと、複数の標準を引いたときに責務が重なり、読者がどれに従えばよいか分からなくなる
- 借りた骨格と自チームの用語の対応表を置く（「本ガイドの X はフレームワークの Y にあたる」）
- 骨格から外した部分は、外した理由を書く

### 9. 例外の扱いを決める

**フローに乗らない案件は必ず出る。禁止せず、受け止め方を決める。** 例外を禁じたガイドラインは、急ぐ場面で黙って飛ばされ、そのまま使われなくなる。

- フロー外で進めてよい条件と、そのとき誰に知らせるかを決める
- フロー外で進めたときは、経路の代わりに **乗せなかった理由** を記録先に残す
- 同じ型の例外が繰り返されるなら、例外ではなくフローが現実に合っていない。次節の更新条件につなぐ

### 10. 運用に載せ、ケーススタディを溜める

公開後は、**実際の対応をフロー経路つきで追記する**。

| 列 | 中身 |
|---|---|
| 案件 | Issue・相談へのリンク |
| 状況 | 何を判断する場面だったか |
| フロー経路 | 「技術判断 → 技術評価（境界と責務）→ 戻せない決定 → 遅延」 |
| 結論 | 何を決めたか |

守ること:

- 経路を書かせることが、**フローの分岐が現実と合っているかの検証** になる。経路を書けない案件が続いたらフローを直す
- 更新条件を書く。「継続的に更新する」だけでは更新されない。**何が起きたら見直すか**（経路に乗らない案件が2回／委ねている原則の改訂／体制変更）を具体的に書く

## 策定後の自己点検

次のいずれかが当てはまったら、手順を足すのではなく **境界と接地を疑う**。

| サイン | 示していること |
|---|---|
| 読んでも誰が決めるか分からない | 境界（決める・委ねる・上げる）が引けていない（2節） |
| 分岐が5つ以上ある | 手順の細かさで分岐させている（4節） |
| 結論に至った経緯が追えない | 入口と記録先を一箇所に固定していない（4節） |
| 領域固有の技術基準が本文に増えていく | 原則へ委ねるべきものを抱え込んでいる（5節） |
| 成果物の粒度が人によって違う | テンプレートと記入例がない（7節） |
| 用語が独自 | 既存フレームワークに接地していない（8節） |
| フロー外で処理された案件が見えない | 例外の扱いを決めていない（9節） |
| ケーススタディが空 | 運用に載っていない。経路を書けない案件が溜まっている（10節） |
| 半年以上更新がない | 更新条件を書いていないか、例外をフローに戻していない（9・10節） |
| 手順だけで目的が書かれていない | 例外の場面で判断できず、手順が形骸化する（1節） |
