# ガイドラインの策定

ガイドラインは、ある活動（技術判断、問い合わせ対応、メンテナンス、アセスメント）を、担当者が変わっても同じ型で進められるようにする手引きである。決めるのは進め方であり、何を良しとするかは原則に委ねる。

狙いは手順の網羅ではなく、判断の再現性である。使われないガイドラインは、内容が薄いからではなく、決めることと委ねることの境界が曖昧で、読んでも次の一歩が決まらないから使われない。

## いつ使うか

- 同じ相談に毎回ゼロから答えている、対応の質が担当者で揺れる、判断がエスカレーションに渋滞している、を解きたいとき
- 設計作業や運用作業（メンテナンス、アセスメント、移行計画）の進め方をチームでそろえたいとき
- 既存のガイドラインが参照されていない、守られていないので作り直すとき

何を優先するか（価値基準）や何を良しとするか（技術基準）を決めるなら `design-principles`、単一の意思決定を記録するなら `adr`、文章の表現は `technical-writing` を使う。

## ガイドラインと原則の分担

チームの規範は、次の 3 つに分けると二重管理にならない。

| 文書 | 答える問い | 例 |
| :--- | :--- | :--- |
| 価値基準の原則 | 軸が競合したとき、何を優先するか | 意思決定の原則（安全性 > 速度 = 再現性、可逆性で判断の重さを変える） |
| ガイドライン | その活動を、どの順で、誰が決めて進めるか | 意思決定ガイドライン、問い合わせガイドライン、メンテナンスガイドライン |
| 技術基準の原則 | その領域で、何を良しとするか | 認証の設計原則、認可の設計原則 |

ガイドラインは、フローと判断の軸と問いを持ち、優先順位と領域固有の基準は原則へリンクする。価値基準の原則がまだ無く、軸の競合で毎回止まるなら、先に `design-principles` で作る。

## 1. 目的を、揃う状態で書く

やること:

1. 誰の、どの活動が、どうそろうかを 1〜2 文で書く
2. そろった状態が複数あるなら、状態ごとに分けて書く（例: リスクを把握できている、対応できている、説明できている）
3. このガイドラインを引いて進めたい実例を 3 つ挙げ、目的がそれを説明できるかを確かめる

守ること:

- 「品質を向上させる」「ベストプラクティスをまとめる」で止めない。測れない目的は、例外の場面で判断の拠り所にならない
- 手順の要約を目的に書かない

## 2. 境界を引く

最初に決めるのはフローではなく境界である。ここが曖昧だと、読者は最後に「で、誰が決めるのか」で止まる。

| 区分 | 内容 | 書き方 |
| :--- | :--- | :--- |
| 決めること | 活動の進め方、仕分け、フロー | 本文で定める |
| 委ねること | 価値基準、技術基準、具体的な操作手順、他チームの実務 | 原則、手順書、他チームの文書へリンクする |
| 上げること | やるか、いつやるか、誰がコストを負担するか | エスカレーション先を役割で名指しする |
| 扱わないこと | 隣の活動、別の文書が定める範囲 | スコープに書く |

やること:

1. 4 つの区分に分けてスコープを書く
2. エスカレーションを「論点の型／例／扱い」の表にする
3. 読者が取り違えやすい隣の活動があれば、違いを表にする（例: リスクアセスメントと脆弱性診断を、対象・問い・見つかるもの・タイミング・出力で比べる）

守ること:

- 技術判断（妥当か、どう作るべきか）と対応コミット（やるか、いつやるか）を分ける。技術的に妥当でも引き受けるかは別の判断であり、混ぜると技術的な結論が組織の都合で歪む
- エスカレーション先は役割で書く。個人名は異動で腐る
- ガイドラインに置くのは判断の型までにする。具体的な操作手順は手順書に置き、リンクで委ねる。手順を抱え込むと、手順の変更のたびにガイドラインが古くなる
- 決まった目安を独断で崩さない場面（例: 外部の都合で告知期間を短縮する）は、上げることとして明記する

## 3. 用語と骨格を既存の標準に接地する

自前の言葉と手順を発明する前に、確立した骨格を探して借りる。

やること:

1. 活動で使う語を、標準の定義に寄せて表にする（用語／定義／例）。標準に定義がない語は、自分たちの整理であると書く
2. 借りる標準を、どの役割で採るかとともに書く（プロセス、採点、洗い出し、観点）
3. 借りた骨格と自チームの用語の対応を書く。骨格から外した部分は、外した理由を書く

守ること:

- 役割を書かずに複数の標準を引かない。責務が重なり、読者がどれに従えばよいか分からなくなる
- 本文で使わない語を用語表に並べない

## 4. 現状の型を書き出す

理想の手順から書き始めない。すでにうまくいった対応から逆算する。

やること:

1. 過去の Issue、相談スレッド、議事録、障害対応の記録から、実際にたどった判断の道筋を集める
2. うまくいった対応を 3 件並べ、共通して通った経路を抜き出す。それがフローの骨格になる
3. うまくいかなかった対応が、どこで止まったか、なぜ揺れたかを書き出す。それが分岐と境界の候補になる

## 5. フローにする

やること:

1. 骨格を分岐つきの図（Mermaid など）にする
2. 最初の分岐に、判断の重さが最も大きく変わる問いを置く（例: 技術判断か、ダウンタイムが発生するか）
3. 各分岐に何を見て分けるかを書き、各終端に何をするかと誰が決めるかを書く
4. 図の直後に、フローの入力と出力、各終端の決定者を文章で書く

守ること:

- 分岐は、判断の主体や重さが変わる点に置く（自チームかエスカレーションか、戻せる決定か戻せない決定か、全体に影響するか一部か）。手順の細かさで分岐させない
- 分岐は 3〜4 に抑える。多いフローは参照されず、結局は勘で進められる
- 答えが分からない分岐は、重い側に倒す（「Yes / 不明」を同じ経路にする）。不明を軽い側に流すと、確かめないまま軽く扱われる
- 入口と記録先を一箇所に固定する。入口が散るとフローに乗る前に流れ、記録先が散ると結論だけが残って経緯が消える
- 結論が否定になる終端ほど、返す内容の書式を決める。見送りや却下は、理由、将来の可能性、代替経路をセットにする。理由だけを返すと交渉が再燃する

## 6. 判断の軸を少数に保つ

やること:

1. 評価の観点を、その活動のどの案件にも使える少数の軸にする（例: 機能／非機能／境界と責務、停止の必要性／影響範囲／日程／実施と撤退／伝達／クローズ）
2. 各軸に、その軸で何を確かめるかの問いを添える
3. 各軸の問いに、推測なしで答えられるかを確かめるよう書く。推測で埋まる問いは、その場で調べる対象になる

守ること:

- 領域固有の技術基準をガイドラインに書き込まない。原則に委ね、ガイドラインには軸と問いだけを置く。書き込むと、領域が増えるたびにガイドラインが肥大し、原則と二重管理になる
- 特定の案件でしか使えない観点は、軸ではなく手順の一部として扱う

## 7. 関係者を名指しする

活動が他チームや外部を巻き込むなら、誰に、なぜ、いつ相談するかを決めておく。

やること:

1. 関係者を「相手／相談する理由／タイミング」の表にする
2. タイミングは日付ではなく、活動の中の出来事で書く（候補日が見えた時点、影響範囲を見立てた時点、実施前までに）
3. 承認が要る相手と、情報を渡すだけの相手を分ける

守ること:

- 相手が担う実務（告知の掲出、問い合わせ対応）と、自分たちが渡す情報の線を引く。何を書くべきかの情報提供が自分たちの責務なら、渡す項目を列挙する

## 8. 前提をそろえるステップを入れる

対象を説明できない状態で進めると、最初の列挙が浅くなり、以降のすべてが的を外す。

やること:

1. 着手前にそろえるもの（対象の目的、構成、既存の状況、過去の事例、期限感）をガイドラインに書く
2. そろっていなければ、この機会に作ると書く。前提資料が初めて作られること自体に価値がある

守ること:

- 挙げた前提ごとに、無いまま進むと何が起きるかを言えるかを確かめる。言えない前提は削る

## 9. 成果物テンプレートを同梱する

テンプレートのないガイドラインは読まれて終わり、成果物の粒度がそろわない。

やること:

1. 各ステップの出力を、コピーして使える表や雛形にする。列がそのままチェック項目になるようにする
2. 終端ごとに雛形を分ける（例: 承認／見送り／引き取り検討の回答、手順書の最低限の項目）
3. 記入例を 1 行入れる。特殊ケースは雛形の注記で扱う

## 10. 例外とフローの外を決める

フローに乗らない案件は必ず出る。禁止せず、受け止め方を決める。

やること:

1. フローの外で扱う案件を名指しする（例: 障害起因や重大な脆弱性の緊急メンテナンスは、インシデント対応を優先する）
2. フロー外で進めてよい条件と、そのとき誰に知らせるかを書く
3. フロー外で進めたときは、経路の代わりに乗せなかった理由を記録先に残すと書く

守ること:

- 例外を禁じない。禁じたガイドラインは、急ぐ場面で黙って飛ばされ、そのまま使われなくなる
- 同じ型の例外が繰り返されたら、例外ではなくフローが現実に合っていないと見なし、更新条件につなぐ

## 11. 運用に載せる

やること:

1. 実際の対応を、フロー経路つきでケーススタディに追記する（案件／状況／フロー経路／結論）
2. 決めきれていない論点を「未確定事項」として、何の事例が増えれば決められるかとともに書く
3. 更新条件を書く。何が起きたら見直すか（経路に乗らない案件が 2 回、委ねている原則の改訂、体制変更）を具体的に書く
4. ガイドラインを AI エージェントに渡して下書きを作らせるなら、エージェントの出力と人の最終判断のずれを記録し、改定の材料にする

守ること:

- 経路を書けない案件が続いたら、フローを直す。経路を書かせること自体が、フローが現実と合っているかの検証になる
- ケーススタディを判断の入力にするときは、先に判断の軸で独立に評価し、結論が出てから前例と照合する。前例から始めると、前提が変わったことに気づけない
- フローを変えたら、既存のケーススタディの経路を新しいフローで引き直す。旧経路は消さずに併記する
- 「運用しながら継続的に更新する」だけで終わらせない。条件が書かれていない文書は更新されない

## 12. 点検

書き終えたら、次の型に当てはまるところがないかを見る。当てはまったら、手順を足すのではなく境界と接地を疑う。

| 型 | 見分け方 | 直し方 |
| :--- | :--- | :--- |
| 決定者が見えない | 読んでも誰が決めるか分からない | 決める・委ねる・上げる・扱わないを引き直す（2 節） |
| 手順書になっている | 操作手順が本文の大半を占める | 手順は手順書に移し、判断の型だけを残す（2 節） |
| 用語が独自 | 標準の語で言い換えられる語を自作している | 標準に寄せ、役割つきで出典を書く（3 節） |
| 分岐が多い | 分岐が 5 つ以上ある | 判断の主体や重さが変わる点だけを残す（5 節） |
| 経緯が追えない | 結論だけが残り、やりとりが散っている | 入口と記録先を一箇所に固定する（5 節） |
| 原則を抱え込んでいる | 領域固有の技術基準が本文に増えていく | 原則へ移し、軸と問いだけを残す（6 節） |
| 粒度がばらつく | 成果物の詳しさが人によって違う | 終端ごとの雛形と記入例を置く（9 節） |
| 例外が見えない | フロー外で処理された案件が記録にない | フローの外と例外の残し方を決める（10 節） |
| 運用に載っていない | ケーススタディが空、半年以上更新がない | 経路つきの追記と更新条件を入れる（11 節） |
