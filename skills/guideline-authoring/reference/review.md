# 規範ドキュメントのレビューチェックリスト

ガイドライン・設計原則・規約をレビューするときの観点。**内容の正しさより先に、判断の再現性を生む構造になっているか** を見る。正しいことが書いてあっても、基準・問い・逸脱の扱いが欠けた文書は使われない。

指摘は Critical / Important / Nice to have で優先度を付ける。文書の構造に関わる欠落（基準・確認する問い・逸脱の扱い・ケーススタディ）は Critical に置く。

## 1. 位置づけ

- [ ] 目的が「誰の・どの判断が・どう揃うか」で書かれているか。「品質を上げる」で終わっていないか
- [ ] どの層の文書か（判断の型／評価の基準／構造の決定／値・手順／現況）が明示されているか
- [ ] 上位・下位の文書との境界が書かれているか。「ここでは決めないこと」がどこへ行くか分かるか
- [ ] 既存文書に足せば済むものを、新規の文書として立てていないか
- [ ] いつ使うかがチーム内・チーム外に分けて書かれているか。外部に準拠を求めるなら語彙が定義されているか

## 2. 収録基準・除外基準

- [ ] 「何を載せるか」の基準が文書内に書かれているか（Critical）
- [ ] 「何を載せないか」が書かれているか。標準の再掲・機械判定可能なルール・数値目標・現況・手順が除外されているか
- [ ] 各項目が基準を通るか。1つずつ当てて確認する
  - [ ] 上位（品質特性・原則）に接地しているか
  - [ ] 従わない選択にも合理性があるか（**誰も反対しない項目は削る**）
  - [ ] 特定の実装・時期を前提にしていないか
  - [ ] 当てはまる判断を2つ以上挙げられるか
  - [ ] 他の項目の言い換え・特殊化になっていないか

## 3. 項目の書式

- [ ] 項目名が動詞で言い切られているか。名詞の羅列になっていないか
- [ ] 「なぜ」が書かれているか。守らなかったときに何が起きるかまで書かれているか（Critical）
- [ ] 「設計で確認すること」があり、Yes/No で答えられる問いになっているか（Critical）
- [ ] 「適切に」「うまく」「十分に」「必要に応じて」など判定できない語が残っていないか
- [ ] 項目数が10を超えていないか。超えるなら統合か確認事項への格下げを提案する
- [ ] 品質特性など分類の軸が、既存の標準（ISO/IEC 25010 等）に準拠しているか。自前分類を発明していないか
- [ ] 標準を引くとき、どの役割で採るか（プロセス／採点／洗い出し／観点）が書かれているか

## 4. 逸脱と更新

- [ ] 逸脱の扱いが書かれているか。禁止していないか（Critical）
- [ ] 単発の逸脱と、繰り返す逸脱で扱いが分かれているか
- [ ] 更新条件が具体的か。「継続的に更新する」だけになっていないか
- [ ] 未決・保留が空欄でなく、決める場所を指しているか

## 5. ケーススタディ

- [ ] 実際に下した判断が3つ以上載っているか（Critical）
- [ ] 逸脱事例が含まれているか。適用に成功した例だけになっていないか
- [ ] 各事例にトレードオフ（受け入れた不利益）と再検討条件があるか
- [ ] 記録（ADR・DesignDoc・Issue）へのリンクがあるか
- [ ] 事例が本体の項目番号を引いているか。引けない事例があるなら項目が足りない

## 6. 運用の検証

レビューの最後に、読み合わせではなく **通しで試す**。

1. 直近の実際の判断を1つ選び、この文書だけを使って結論まで辿れるか試す
2. 辿れなければ、どこで止まったかを指摘する（項目不足／粒度違い／問いが曖昧）
3. 結論が実際の判断と食い違うなら、文書と現実のどちらを直すかを提起する

## 7. 文章

`technical-writing` skill の6つの文書特性で見る。規範ドキュメント固有では次を優先する。

- [ ] 一文一義か。1つの項目に2つの規定が入っていないか（入っていれば分割）
- [ ] 事実・規定・意見が区別されているか
- [ ] 表記が揺れていないか（同じ概念に複数の呼称が使われていないか）
- [ ] 機密情報（具体的な IP、認証情報、未公開の名称）が混入していないか
