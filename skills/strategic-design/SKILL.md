# 戦略的設計

ドメインをサブドメインに分けて、事業にとっての重要さで分類する。分類をもとに、どこに人と時間をかけ、何を作り、何を買うかを決める。あわせて、モデルの境界と、境界どうしの関係を決める。

## いつ使うか

- 新しいプロダクトや事業で、どこから作るか、何に力を入れるかを決めたいとき
- 既存のシステムを分割する、またはチームを分けるとき
- 内製するか、既製品や外部サービスを使うかを決めたいとき
- 複数のチームやシステムの関係が複雑になり、整理したいとき

業務の流れと境界の候補を見つけるところは `event-storming`、分割を含むアーキテクチャの方針を決めるところは `architecture-strategy` を使う。

## 1. 問題と解決を分ける

やること:

1. 問題空間と解決空間を分けて考える
   - サブドメイン: 事業が扱う業務の領域。問題空間に属する
   - 境界づけられたコンテキスト: 一つのモデルと言葉が一貫して通じる範囲。解決空間に属する
2. 先にサブドメインを決め、そのあとでコンテキストを決める

守ること:

- 既存のシステムやチームの分け方を、そのままサブドメインとして扱わない

## 2. サブドメインを洗い出す

やること:

1. 事業が提供する価値と、それを支える業務を書き出す
2. 業務を、まとまった能力（何ができるか）の単位に分ける。例: 受注、在庫、配送、請求、認証
3. イベントストーミングの結果があれば、ピボットイベントや言葉の変わり目を手がかりにする

## 3. 分類する

やること:

1. サブドメインごとに、次の問いに答える
   - これが他社より優れていることが、顧客に選ばれる理由になっているか
   - 他社と同じやり方で困らないか
   - 既製品や外部サービスで置き換えられるか
2. 答えをもとに分類する

   | 分類 | 意味 | 判断の目安 |
   | :--- | :--- | :--- |
   | コアドメイン | 事業の競争力の源で、他社と差をつける領域 | 選ばれる理由になっている。他社と同じでは困る |
   | 支援サブドメイン | 事業に必要で固有の事情があるが、差はつかない領域 | 他社と同じでよいが、ちょうどよい既製品がない |
   | 汎用サブドメイン | どの事業でも同じように必要な領域 | 既製品や外部サービスで置き換えられる |

3. 分類に迷うものは、差別化の度合いとモデルの複雑さの 2 軸に置いて比べる
4. 分類ごとに理由を一文で書く

守ること:

- 技術的に難しいことと、コアであることを混同しない。難しい汎用サブドメインはよくある
- すべてをコアにしない。コアは少数に絞る
- 分類は事業戦略で変わる。前提が変わったら見直す

## 4. 方針を決める

やること:

1. 分類ごとに方針を決める

   | 分類 | 作り方 | 人 | モデリング |
   | :--- | :--- | :--- | :--- |
   | コアドメイン | 内製する | 最も力のある人をあてる。ドメインエキスパートと近くで作る | 深く作り込み、継続して磨く |
   | 支援サブドメイン | 内製するか外注する。簡素な作りでよい | 必要な分だけ | 簡素に保つ |
   | 汎用サブドメイン | 既製品や外部サービスを使う | 導入と連携の分だけ | 外部のモデルに合わせる |

2. 今の投資配分と比べ、ずれているところを書く

守ること:

- 汎用サブドメインを作り込まない。作り込むなら、コアと言える理由を先に書く
- コアドメインを外注しない。外注するなら、差別化をどう守るかを先に書く

## 5. 境界づけられたコンテキストを決める

やること:

1. 同じ言葉の意味が変わるところで、コンテキストを分ける。例: 「顧客」が営業と請求で違うものを指す
2. コンテキストごとに、使う言葉と意味を書く（ユビキタス言語）
3. コンテキストを担当するチームを決める。一つのコンテキストは一つのチームが持つ
4. サブドメインとコンテキストの対応を書く。1 対 1 が理想だが、既存のシステムではずれることがある。ずれは、そのまま書く

守ること:

- 画面、データベース、技術の層で境界を切らない。言葉とルールのまとまりで切る

## 6. コンテキストの関係を決める

やること:

1. コンテキストどうしの依存を書き、どちらが上流（提供する側）でどちらが下流（使う側）かを決める
2. 関係ごとに、[reference/context-mapping.md](reference/context-mapping.md) から関係の型を選ぶ
3. コンテキストマップとして図にする

守ること:

- 下流がコアドメインで、上流の変更に振り回されるなら、腐敗防止層を置いてコアのモデルを守る

## 7. 点検する

| 型 | 見分け方 | 直し方 |
| :--- | :--- | :--- |
| コアを外に出している | 差別化の源を外注や既製品に任せている | 内製に戻すか、差別化を守る手段を書く |
| 汎用を作り込んでいる | 認証や請求など、どこでも同じものに多くの人と時間を使っている | 既製品や外部サービスに置き換える |
| 全部がコアになっている | 分類が機能しておらず、投資の優先度が決まらない | 選ばれる理由に直結するものだけを残す |
| 技術の層で切っている | フロント、API、データベースでコンテキストを分けている | 言葉とルールのまとまりで切り直す |
| 一つのモデルが肥大している | 一つの言葉に複数の意味が混ざり、変更がどこに効くか分からない | 意味ごとにコンテキストを分ける |
| 上流の変更が下流を壊す | 外部や他チームの変更で、下流のモデルが崩れている | 腐敗防止層を置くか、公開する形を決めて合意する |
| 分類が古いまま | 事業の方針が変わったのに、分類と投資配分が変わっていない | 3 からやり直す |

## まとめ方

次の形で残す。

- サブドメインの一覧: 名前、説明、分類、分類の理由、対応するコンテキスト、方針
- コンテキストマップ: コンテキスト、担当チーム、関係の型を図にする
- 用語集: コンテキストごとの言葉と意味
